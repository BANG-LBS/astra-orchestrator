# Astra 智能编排：设计与迭代记录

这份记录说明 Astra 智能编排为什么出现、经历了哪些取舍，以及最终能力是如何形成的。它不是完整开发日志，而是经过整理和脱敏的设计脉络。

## 1. 从个人额度问题开始

最初目标是让 GPT-6 Astra 保留在 root 位置，负责拆解、困难推理、架构和最终决策，同时把适合独立处理的普通工作优先交给 GPT-5.6 Luna，必要时使用 Terra。

第一版直接通过全局配置和 `AGENTS.md` 实现，并进行了小型只读 child 路由测试。这证明分工路线能够运行，但也暴露出全局规则会影响非 Astra 任务的问题。

## 2. 控制多代理本身的成本

进一步讨论后发现，子代理并不天然节省使用量。大量复制历史、代理之间反复解释、递归派生以及 root 重做 child 的扫描，都可能产生额外成本。

因此增加了：

- 委派收益判断；
- 最小上下文和 `fork_turns="none"` 优先；
- 禁止未经授权的递归派生；
- 同范围后续工作复用原 child；
- 精简 child-to-root 交接；
- root 只对高风险或有争议的结果做定点验证。

开发过程中曾考虑固定 Luna reasoning、固定 child 数量，以及只报告一个 blocker。由于这些规则可能过度限制不同任务，最终没有采用。多个已经确认的独立 blocker 应当全部报告，推测性问题则归入 risks。

## 3. 从全局配置改为显式 Skill

全局 `AGENTS.md` 无法只在 Astra 任务中自动生效。为了避免影响 GPT-5.6 的普通使用，完整编排规则被移入显式调用的 `$astra-orchestrator` Skill，并设置：

```yaml
policy:
  allow_implicit_invocation: false
```

中文界面名称为“Astra 智能编排”，内部标识继续使用兼容性更好的 `astra-orchestrator`。

## 4. 处理多轮持续性

为了让同一项未完成任务中的补充、纠正和继续执行保持编排状态，项目保留了一个可选的轻量 `AGENTS.md` 门控。完整规则仍在 Skill 内，门控只负责激活和退出边界。

## 5. 撤回未经验证的“优化”

后续复查撤回了多项缺乏依据的固定规则，包括强制把 Skill 压缩到特定词数、固定扫描与代码修改的模型分工、在 Skill 中声明平台缓存策略，以及进一步固定 reasoning 和并发数量。

最终保留的改进集中在真实失败模式：

- 先判断是否值得委派；
- Luna 结果受阻、明显不完整或缺少关键证据时，允许升级一次 Terra；
- 交接采用核心必填、其余字段按需；
- 路由验证移到只有用户要求时才读取的参考文件。

## 6. 保留用户选择的 Astra reasoning

最初把 Astra `low` 当作固定条件，后来调整为经济型建议。用户可以根据任务选择 reasoning 等级；只要 root 仍是 GPT-6 Astra，Skill 就继续生效。

## 7. 用真实任务验证

项目最终使用一个经过匿名化的真实业务任务，对比了基准组（原生Astra）、工具组（Astra智能编排开启）和人工深度组（原生Astra+深度提示词）三种方式。

测试没有证明固定的额度节省比例。它较清楚地支持了另一个价值：Skill 能把专业工作流封装起来，让不熟悉复杂提示词的用户也更容易获得完整、可交付的结果。

三组测试的范围、消耗和结论见[个人真实案例测试](../examples/real-world-evaluation.md)。

## 最终形成的能力

经过这些迭代，Skill 的重点不再是“尽可能多地派出子代理”，而是让 Astra 判断什么时候值得委派、给 child 多少上下文、何时需要升级，以及最终应该验证到什么程度。它把这些原本需要用户写进复杂提示词的要求，收进了一套可重复使用的工作流程。
