# Astra 智能编排：设计与迭代记录

这份记录说明 Astra 智能编排为什么出现、经历了哪些取舍，以及最终能力是如何形成的。它不是完整开发日志，而是经过整理和脱敏的设计脉络。

## 1. 从个人额度问题开始

最初目标是让 GPT-6 Astra 保留在 root 位置，负责拆解、困难推理、架构和最终决策，同时把适合独立处理的普通工作优先交给 GPT-5.6 Luna，必要时使用 Terra。

第一版直接通过全局配置和 `AGENTS.md` 实现，并进行了小型只读 child 路由测试。这证明分工路线能够运行，但也暴露出全局规则会影响非 Astra 任务的问题。

## 2. 控制多代理本身的成本

进一步讨论后发现，子代理并不天然节省使用量。大量复制历史、代理之间反复解释、递归派生以及 root 重做 child 的扫描，都可能产生额外成本。

因此增加了：

- 委派收益判断；
- 最小上下文和 `fork_turns="none"` 优先；
- 禁止未经授权的递归派生；
- 同范围后续工作复用原 child；
- 精简 child-to-root 交接；
- root 只对高风险或有争议的结果做定点验证。

开发过程中曾考虑强制固定 Luna reasoning、固定 child 数量，以及只报告一个 blocker，后来撤回了这些硬限制。V2 的思考强度属于可被用户覆盖的默认选择。多个已经确认的独立 blocker 应当全部报告，推测性问题则归入 risks。

## 3. 从全局配置改为显式 Skill

全局 `AGENTS.md` 会进入其他模型的任务上下文，原先的全局编排规则可能影响普通使用。为收窄适用范围，完整规则被移入显式调用的 `$astra-orchestrator` Skill，并设置：

```yaml
policy:
  allow_implicit_invocation: false
```

中文界面名称为“Astra 智能编排”，内部标识继续使用兼容性更好的 `astra-orchestrator`。

## 4. 处理多轮持续性

为了让同一目标下的补充、纠正、复核和交付后的修改保持编排状态，项目保留了一个可选的轻量 `AGENTS.md` 门控。结束一轮回复或交付一版不单独构成退出；任务明确收尾、显式关闭、切换目标或切换离开 Astra 才退出。手动启用时不额外播报，退出时只简短说明一次。交接与上下文压缩摘要保留状态、目标和 Skill 路径，必要时重新读取完整规则。这是指令层面的延续约定，没有新增独立运行时开关，也不要求用户额外确认完成。

## 5. V1 阶段：撤回未经验证的“优化”

后续复查撤回了多项缺乏依据的固定规则，包括强制把 Skill 压缩到特定词数、固定扫描与代码修改的模型分工、在 Skill 中声明平台缓存策略，以及进一步固定 reasoning 和并发数量。

当时保留的改进集中在真实失败模式：

- 先判断是否值得委派；
- Luna 结果受阻、明显不完整或缺少关键证据时，允许升级一次 Terra；
- 交接采用核心必填、其余字段按需；
- 路由验证移到只有用户要求时才读取的参考文件。

## 6. 保留用户选择的 Astra reasoning

最初把 Astra `low` 当作固定条件，后来调整为经济型建议。用户可以根据任务选择 reasoning 等级；只要 root 仍是 GPT-6 Astra，Skill 就继续生效。

## 7. V1：用真实任务观察交付差异

V1 使用一个经过匿名化的真实业务任务，对比了基准组（原生Astra）、工具组（Astra智能编排开启）和人工深度组（原生Astra+深度提示词）三种方式。

测试没有证明固定的额度节省比例。这些观察支持继续把工作流封装进 Skill、减少手写过程要求的负担；它们没有单独验证所有新手的上手优势。

三组测试的范围、消耗和结论见[个人真实案例测试](../examples/real-world-evaluation.md)。

## 8. V2：更新子模型与选路

GPT-6 Sol 和 GPT-6 Luna 推出后，子任务模型从 GPT-5.6 Luna／Terra 更新为 GPT-6 Luna／Sol。选路也从“先 Luna、必要时升级”调整为按任务难度直接判断：清晰、可重复的工作使用 Luna；明显需要复杂规划、多步骤执行或深入验证的工作直接使用 Sol。Luna 结果受阻或明显不完整时，仍允许检查缺口后最多升级一次 Sol。

根据用户偏重质量的选择，本项目把 Luna 子任务的默认请求设为 `max`；Sol 以 `medium` 为起点，对深度审查、复杂实现等高难度子任务请求 `xhigh`。这些是项目默认策略，用户可以指定其他受支持的强度；Astra root 保留用户选择的思考强度。V1 的历史观察不能用于推断这次模型更新后的额度效果。

一次路由验证还暴露出激活边界问题：仅调用 Skill 不会把当前对话切换成 Astra。此后要求先核对运行时主模型；若无法读取，则请用户明确确认已选择 Astra，再启用编排。

## 9. V2：加入成本与使用体验的实际记录

随后使用同一原始表格、相同简短业务提示和 Astra `xhigh`，串行运行原生组与 V2 组。两组均完成较完整的交付；V2 额外核验了当前来源，并提供组合筛选。用户阅读后认为其报告更易理解、方便使用。

按统一 Standard API 单价重算根与子任务的已有 token，排除监测后，原生组约11.35美元，V2 组约9.33美元，低约17.8%；总 token 则多22.1%。素材复用、不同中断时点、额外工作范围及非盲评等限制随结果一并公开，不把该结果换算成已验证的套餐额度节省。

用户决定不再追加验证实验，后续根据真实业务反馈迭代。完整方法和限制见[个人真实案例测试](../examples/real-world-evaluation.md)。

## 10. V2.1：将 Sol 子模型更新为 GPT-6.1 Sol

2026年10月1日，按用户选择，把当前 Sol 子任务的请求标识从 `gpt-6-sol` 改为 `gpt-6.1-sol`。GPT-6 Astra 继续负责主控，GPT-6 Luna 继续处理清晰、可重复、可独立验证的工作；复杂任务和一次 Luna 升级使用 GPT-6.1 Sol。Sol 默认请求 `medium`，深度审查和复杂实现等任务请求 `xhigh`，其余编排与持续门控规则沿用原版。

[GPT-6.1 Sol 官方模型页](https://developers.openai.com/api/docs/models/gpt-6.1-sol)支持这些思考强度。按2026年10月1日核对的 Standard API 文本价格，普通输入和输出仍为每百万 token 2美元和10美元，缓存输入为0.10美元；[GPT-6 Sol](https://developers.openai.com/api/docs/models/gpt-6-sol)的对应缓存输入价为0.20美元。这些是 API 单价，不用于换算订阅额度。

按用户要求，此次更新不新增模型对照或路由实测，仅做文件格式与一致性检查。V2 的历史实验继续保留当时使用的 GPT-6 Sol 名称、单价和结果。

## 最终形成的能力

经过这些迭代，Skill 的重点不再是“尽可能多地派出子代理”，而是让 Astra 判断什么时候值得委派、给 child 多少上下文、何时需要升级，以及最终应该验证到什么程度。它把这些原本需要用户写进复杂提示词的要求，收进了一套可重复使用的工作流程。
